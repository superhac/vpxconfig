# VPinConfig

A small local web app that walks you through the VPinballX settings for a three-screen cabinet and
writes a new ini file.

```
./run.py            # then open http://localhost:1111 in Chrome
```

- **Base:** by default `VPinballX.ini` in this folder (the default generated by `VPinballX_BGFX -h`, plus the settings VPinConfig manages that `-h` leaves out, such as the extra plugin sections; `VPinballX.ini.vpconfigbackup` is the original, and `tools/sync_base.py` adds anything missing). On the Start page you can pick an existing `VPinballX.ini` instead, using the built-in file browser (it lists the folders of the machine running this app, not the browser's) or by typing the full path; the wizard then fills its fields from that file and edits a copy. Blank means the project's file. When you load a file, a copy is saved next to it as `<name>.vpconfigbackup` (an existing backup with different content is never overwritten; a timestamped one is made instead, and if the backup can't be written the load fails). The base file is never modified, and the project's `VPinballX.ini` always defines the wizard's labels and defaults.
- **Output:** by default `~/.local/share/VPinballX/10.8/VPinballX.ini`, where VPX keeps its settings (VPX 10.8 uses a folder per minor version). On the Start page you can type another full path or Browse to override it, just like the base file. Review & Save writes it: an existing file is first copied next to itself as `<name>.vpconfigbackup` (never overwriting a different backup), its permissions are kept, missing folders are created, the page asks before replacing a file, and the project's own base `VPinballX.ini` can never be chosen. Keys the wizard doesn't cover are copied through unchanged from the base.
- **Scope (for now):** only the settings that differ in the reference cabinet config. Everything else stays at the VPX default. See `docs/PLAN.md`.
- **No dependencies:** running from source needs only Python 3.12+ and its standard library. The only fixed location is VPX's own settings file (the output default above); everything else is relative to this folder or chosen by you.
- **Local only:** listens on 127.0.0.1 by default (`--host` / `--port` to change). It runs a fixed set of read-only system commands (currently `wayland-info`) and can only write the chosen output file (plus its `.vpconfigbackup`), backups next to a loaded base file, and `state.json`.

## Running the executable

Each release has a single file, `vpinconfig` (Linux x86_64 only), that needs no Python. The version is in the release's name and in `--version`:

```
chmod +x vpinconfig
./vpinconfig          # then open http://localhost:1111 in Chrome
./vpinconfig --version
```

`--host` and `--port` work as above. Stop it with Ctrl+C, or with the **Shut down** button at the bottom of the page's sidebar (it asks first; your answers are already saved as you type, but the ini file is only written when you click Write on the Review page). Next to the executable is a `.sha256` file to check the download. Because the executable unpacks itself into a temporary folder that is deleted when it exits, your answers are kept in `~/.config/vpinconfig/state.json` (or under `$XDG_CONFIG_HOME` if that is set) instead of next to the program. It is not signed.

## How it works

| Piece | File |
|---|---|
| Wizard steps and which keys each covers (one page per plugin, under a "Plugins" header) | `vpinconfig/steps.py`, `vpinconfig/plugins.py` |
| Label, help, default, range and dropdown options | read from the comments in `VPinballX.ini` |
| Line-preserving ini editor | `vpinconfig/ini.py` |
| System commands (monitor detection) | `vpinconfig/system.py` |
| Folder listing for the file browser | `vpinconfig/fs.py` |
| HTTP server and JSON API | `vpinconfig/server.py` |
| UI | `web/` |

Your answers are saved to `state.json` so a restart keeps them. A blank answer means "leave at the VPX default".
The output is always the whole base file with your changes applied. A value equal to VPX's own default is left blank (a blank value already means the default), so an untouched setting never gets an explicit value.

## Adding a setting

A setting is a `Setting(...)` (see `vpinconfig/settings.py`); `vpinconfig/steps.py` decides which page and group shows it.
Add one line to a group in `steps.py`:

```python
# Key that is in VPinballX.ini: label, help, default, options and range come from its comment.
S("Player", "BGSet")

# ...same, but overriding some of it:
S("Player", "PlayfieldFullScreen", label="Playfield FullScreen",
  options=[("0", "Disabled"), ("1", "Enabled")], description="Enable borderless fullscreen mode.")

# Key that is NOT in the template (e.g. written by a plugin): describe it fully.
S("Backglass", "Priority.PUP", type="int", label="PUP priority", default="0", min="0", max="9",
  description="Which content is shown on the backglass window.")
```

| Attribute | Meaning |
|---|---|
| `section`, `key` | where it lives in the ini |
| `label`, `description`, `notes` | what the user sees |
| `type` | `bool`, `int`, `float`, `text`, `select` or `display` (a monitor dropdown). Inferred for keys in the template |
| `default` | VPX's default; a blank ini value means this |
| `options` | acceptable values for `select`/`bool`: `[("0", "Disabled"), ("1", "Enabled")]` |
| `min`, `max` | acceptable range for `int`/`float` |
| `placeholder` | grey hint in an empty box (`""` for none) |
| `initial` | answer the wizard starts with (a suggestion; the user can change or clear it, and loading a base file replaces it) |

Anything left out is read from the comment above the key in `VPinballX.ini`. A key that isn't in that file must at least have a `type`.
Definitions are checked at startup (unknown type, default not among the options, min > max, duplicate keys, ...), and values are checked
against `options` / `min` / `max` on the Review page: an unacceptable value is listed and the file isn't written until it's fixed.
Your answers are stored in `state.json` as a flat `"Section.Key": "value"` map, so adding a setting needs no migration.

**Keep the base file in step:** a setting defined in code should also be in `VPinballX.ini` (with a comment in its format). Run `tools/sync_base.py` after adding a `Setting`; a test fails until the base file has the key. The tool adds the missing settings, and fills in the starting answers (`initial`) that differ from VPX's default (for example the ScoreView priorities), so that a fresh start compares equal to the base file and Review shows no changes. It never overwrites a value, and running it twice does nothing. If you regenerate `VPinballX.ini` with `VPinballX_BGFX -h`, run the tool afterwards to put the added settings back.

## Adding a system command

Add a function to `COMMANDS` in `vpinconfig/system.py`. It is served at `/api/system/<name>`. Commands take no user input and run without a shell.

## Building the executable

```
tools/build.sh                                       # -> dist/vpinconfig and dist/vpinconfig.sha256
tools/smoke_test_exe.sh dist/vpinconfig
```

`tools/build.sh` installs PyInstaller (pinned in `requirements-build.txt`) into a virtual environment in `.venv/`, created on the first run, and never into the system Python. `vpinconfig.spec` says what is bundled: the `web/` folder and the base `VPinballX.ini`. The smoke test starts the executable with a throw-away home and config folder and checks the version, the pages, the wizard and where the answers are kept.

## Versioning and releases

The version is set in one place, `__version__` in `vpinconfig/__init__.py` (the first version is `0.5`). It is shown by `--version`, in the start-up message and in the page's sidebar. A release is named by a git tag `v<version>`, for example `v0.5`; the executable file itself is always just `vpinconfig`.

The `Release` workflow (`.github/workflows/release.yml`) builds on Ubuntu 22.04 (an older glibc, so the executable runs on older distributions too), runs the unit tests, smoke tests the executable, and can publish a GitHub release with `vpinconfig`, `vpinconfig.sha256` and generated release notes. Only Linux x86_64 is built: the wizard uses Linux tools (`wayland-info`) and VPX's Linux settings location. There are two ways to run it:

- **Push a tag.** Set `__version__` (skip this for `0.5`, which is already set), commit, then `git tag v0.5 && git push origin v0.5`. The workflow first checks that the tag matches `__version__`; a mismatch fails before anything is built. It then builds and publishes the release.
- **Run it by hand.** On GitHub go to Actions, Release, Run workflow, and type the **version** (for example `0.5`). That version is put into the code for that run only, so the executable reports it without you editing anything, and the run builds, tests and uploads the executable as a workflow artifact. Tick **Publish** as well to also create the release `v<version>` (and its tag, on the commit that was run). Publish is off by default, and a version that already has a release is refused before the build starts.

To check a download: `sha256sum -c vpinconfig.sha256`.
